# Nutrition Agent 第一版 Python Demo 範圍

## 目標與工作區

依 Isaac 的備餐流程，建立可持續保存資料的單人 Python demo。新工作區為 `/Users/wolverine/Develop/nutrition-agent`，最終產品介面為 iOS App。互動與後續評估共用相同工具與資料服務。

本文件整合需求訪談、第一版範圍確認與 2026-11-17 的設計討論。先前版本由 Git 保留，原始訪談在 canonical Obsidian vault。

## 已確認功能

| 能力 | 第一版行為 |
|---|---|
| 個人設定 | 保存每餐與每日營養目標、時區、鍋具與餐盒容量。目標預設沿用，直到要求更改。 |
| 食材庫存 | 規劃前列出庫存確認，優先使用現有食材；文字購入資訊確認後入庫。 |
| 料理選擇 | 四份實際舊食譜作為基礎資料，推薦時解釋困難操作、鍋具／分批與估計成本。 |
| 營養客製化 | 選料理後調整用量及少量替換，保留料理特色。模型提案、程式驗算、有限次迭代，再確認整份食譜。 |
| 烹調協助 | 提供完整食譜與步驟，支援基本問答與分批安排。 |
| 完成備餐 | 確認實際用量、盒數及組成；同次烹調不同組成分不同批次，食材總用量只扣一次。 |
| 加餐 | 確認搭配與每餐用量後保存於批次，食用時預設計入並扣除食材；使用者可指定例外。 |
| 食用 | 資訊明確時直接記一盒＋實際加餐，計入當日營養及更新剩餘。不明批次先澄清。 |
| 庫存差異 | 食用時加餐不足，先釐清，再一起更新必要校正、食用與扣除。 |
| 更正 | 先預覽並核准，再更正日期、批次或加餐，依歷史快照同步調整營養、盒數及食材。 |
| 查詢 | 每日四項營養與個人目標的進度，各批剩餘盒數、每盒營養與預設加餐後的整餐營養。 |

預設六餐、同一道料理，可指定其他餐數或變化。每餐需同時符合熱量目標 95%–105%、蛋白質 100%–110%、碳水與脂肪各 90%–110% 才標示達標。此為產品規則，容差比較採完整計算值，數值顯示才四捨五入。

## 四道基礎食譜

1. 日式雞胸咖哩，完整便當及純咖哩分不同批次。
2. Nikujaga 豬里肌便當，原六份與後續七等份方案分別保存來源狀態。
3. BBQ 豬肩肉 Mac & Cheese，含花椰菜與無花椰菜分不同批次。
4. 蒜香菇菇牛肉雞胸炊飯，六餐分兩鍋。

原始檔名、路徑、SHA-256 與資料缺口詳見實作計畫。營養採實際商品標示優先、一般食材使用 USDA，缺資料時標估算；歷史 PDF 數值需核對來源。成本保存計價基準，缺漏部分清楚標示。

## 環境與模型

- Docker Compose 管理 Python app 與持久化 PostgreSQL，模型使用自己的 OpenAI API。
- 第一版預設 gpt-6-luna，CLI --model 優先於 OPENAI_MODEL，最後回退到預設。
- 每次執行保存模型及參數，同輪評估固定設定。
- 主流程階段及確認狀態由應用程式維護，階段內允許模型依結果選擇工具。
- 技術建議採 Python 3.12、PostgreSQL 18、psycopg 3 與 SQL migrations。具體重試上限與版本在 development cases 驗證後凍結。

## 版本取捨

- 第一版使用少量附來源的固定食材、價格與食譜資料。預設 Walmart，提供已核對的商品連結及所需數量，由使用者加入購物車。
- 即時查貨與自動找替代品、訂單截圖辨識、完整逐步烹調陪伴、風味回饋循環及 iOS App 為後續版本。
- 外食、零食與飲料紀錄留到後續版本，主動提醒目前暫不需要。
- 課程要求的雲端網頁、正式 benchmark、安全測試與 baseline 比較依 course-requirements 另行追蹤。

## 完成條件

- 自然語言可完成料理選擇、客製化確認、烹調成果確認、加餐與食用、更正及查詢。
- 同次烹調產生多批成品，庫存只扣一次，營養與成本按組成分配。
- 加餐方案在食用時影響營養及庫存，未採用建議不增加已攝取量。
- 拒絕、失敗、重試、過期預覽與同時操作維持資料一致。
- 重建容器後仍可查詢資料，備份可在獨立環境還原。
- 測試與示範使用隔離資料，具備來源／估算標示與實際完成證據。
